# Read API answers are edge-cached in Workers Cache and purged by tag; the database cache stays off

Every successful Read API answer carries `Cache-Control: public, max-age=0, s-maxage=3600` and a `Cache-Tag` header naming what it was built from: `cms`, the page or item itself, its collection, the site, or `cms:routes` for redirects, not-found answers and sitemaps. A page also carries the tags of the pages and items its links point at, so a renamed target refreshes every page linking to it. Every answer that resolves media carries `media:<id>`, including SEO images and missing media ids. Headers stay under 8 KiB, below Cloudflare's 16 KiB limit. Above 8 KiB, page and item tags collapse into `cms:routes`, and media tags collapse into `media`. Every page or item publish, unpublish, and delete purges `cms:routes`. Every media edit, replacement, archive, and restore purges `media`. Invalidation stays complete but becomes coarser. An answer still above 8 KiB after collapse is private and uncached, with no Cache-Tag. The public site's SSR copies the tags onto its HTML (ADR 0004).

The cache is the Worker's own [Workers Cache](https://developers.cloudflare.com/workers/cache/): the host's Wrangler config sets `"cache": { "enabled": true }`, and Cloudflare answers a cached URL without running the Worker. Publishing, unpublishing, deleting, redirect writes, and media mutations enqueue tags in core's `cache_purge` outbox inside their write transactions. `CachePurge.afterCommit` attempts the purge after the outermost transaction commits. A rollback discards both the row and its attempt. Core owns this port because media cannot depend on CMS. Hosts provide `workersCachePurge(ctx)` from `@opulonjs/core/workers`, or their own `CachePurger` layer whose effect fails on refusals and errors.

The adapter calls the invocation's [`ctx.cache.purge({ tags })`](https://developers.cloudflare.com/workers/cache/purge/). No zone or API token is involved. A purge is scoped to the Worker entrypoint that runs it. A public site rendered in the same Worker shares the Read API's invalidation when it calls the composed handler with its own `ctx`. Workers Cache uses the Free tier's purge limits regardless of plan: 5 requests per minute, bursts of 25, and 100 tags per request. The adapter splits tags into groups of 100 and propagates errors and refusals to the outbox. An invocation without Workers Cache needs no purge and succeeds.

The `core.cache_purge_sweep` task runs every five minutes through the host's existing scheduled handler. Each sweep claims at most 50 due rows with `for update skip locked`, merges their tags, and leases those rows for five minutes. One attempt has a 20-second deadline across all tag batches, well inside its lease and the Worker's `waitUntil` lifetime. Each row gets at most three attempts, including its immediate attempt and any attempt interrupted by a crash. Failed attempts retry after five minutes. A final attempt whose lease expires without an outcome becomes failed and is never retried. Success deletes the row. Purging again after a successful purge interrupted before deletion is harmless.

Queued rows and exhausted failures remain visible until one hour after they were created. This matches the Read API's `s-maxage=3600`, so exhausted failures remain visible while their original cached answers may still exist. The sweep removes expired rows in batches of 50. `GET /api/cache-purges` returns at most 50 status rows without document tags or provider diagnostics, plus aggregate counts and the latest expiry across all active rows. The aggregate keeps exhausted failures visible even when newer writes fill the bounded list. The endpoint requires sign-in and checks the user's permissions against producer contributions to core's existing extension-point machinery. Media contributes `media.upload` and `media.archive`; CMS contributes its view, edit, and publish permissions. Core does not import downstream modules or grant permissions. The shared admin `CachePurgeNotice` shows the notice in English or Slovak on CMS screens, publish controls, and the media library and details. It refreshes after actions and every 30 seconds. While media details are open, only the details notice is mounted. Media view-only staff do not see an unavailable warning for status they cannot access. Storage keeps bounded diagnostics for operators. Editors receive fixed, safe failure messages and the cache expiry time.

A durable queue was previously rejected because it required scheduled work. TSPACK-45 reuses the host's module tasks to retry lost or refused purges and make unresolved failures visible. No event bus or reverse scan of CMS documents is needed. Cloudflare exposes `ctx.cache` on every handler's execution context, so the scheduled handler uses the same host adapter without an opportunistic request sweep.

Workers Cache keys a response by its URL only (cookies and `Authorization` are not part of the key) and caches a 200 without `Cache-Control` for two hours. So answers are private unless declared public. `createWorker` answers anything without its own `Cache-Control` with `private, no-store`. On a Nuxt site, `cmsNitroHooks` makes a page public only when the page calls `useCmsPublicPage()` during its render, declaring that nothing in it depends on the visitor: cms reads alone cannot prove that, since the same render may show the visitor's session. Even then the page stays `private, no-store`, untagged, if any read was `?preview`, carried credentials or was not public. Every other Nuxt answer without a `Cache-Control` gets `private, no-store` at the Worker's response boundary: `cmsNitroPlugin` wraps `nitroApp.localFetch`, through which the cloudflare-module preset answers every request, so the default holds however the answer was sent (`send`, `sendStream`, `sendRedirect`, `sendWebResponse`, `res.end`, route-rule redirects, error pages). Nitro's `beforeResponse` hook was not enough: direct sends skip it. A `Cache-Control` the host or an earlier hook set is never replaced, so no header value has to be told apart from a default. Nuxt's error pages are `private, no-store` too: Nitro renders them through the same `localFetch` and copies that answer's headers.

The host's Hyperdrive configuration must have query caching disabled (`wrangler hyperdrive create <name> --caching-disabled`, or `update --caching-disabled`). Hyperdrive caches reads for up to 60 seconds and never invalidates on write, so a purged page would be rebuilt from stale rows. One binding serves the Worker, so admin reads after a write are fresh too.

We rejected purge-by-URL (the old sites' hardcoded path lists missed pages that link to a changed one) and an in-memory server cache (per isolate, never purged). We first purged through the zone API (`POST /zones/<zone>/purge_cache` with a token), but a Worker's own responses are not stored in the zone cache, and no zone-level purge reaches Workers Cache (TSPACK-38). A replaced file gets a new URL and the old one keeps serving. Media tags now purge cached answers that still point at that old URL. Archive and restore also purge, although archived media continues to resolve and serve. Decided in TSPACK-11 and TSPACK-35, revised in TSPACK-38 and TSPACK-45.
