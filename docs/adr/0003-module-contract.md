# Modules are described twice, by id, and other packages' extension points are contributions

Every module, whether a package or a host module, has one id that prefixes its schema, API group, permission keys, audit actions, messages and admin routes. It is described once for the server (`defineModule` in core) and once for the admin (`defineAdminModule` in admin). The host composes two lists, one per bundle. The two lists are linked only by id and a shared build id. The shell imports no module implementation; its shared module contract is the client-safe `core/api`. Core's contract holds only what core owns: API, layers, migrations, permissions, audit actions, scheduled tasks. Extension points that belong to another package (email templates, sitemap sources) are contributions, built with that package's helper and collected by it. A contributor must therefore depend on the owner. cms definitions are host options passed to both bundles from one client-safe file, not contributions. Authorization fails closed: composition rejects any non-public endpoint that lacks the auth middleware and exactly one declared policy, and privileged services check permissions again.

We rejected core knowing every extension point (it would stop being minimal and framework-neutral), the host hand-wiring each one into the owner's options (a package could not ship its own templates), and serving cms definitions to the admin as JSON (loses types). One composition entry for both bundles is impossible, since server and browser code cannot share it. Decided in TSPACK-7, reviewed independently by gpt-6.1-sol and gpt-6-astra.

TSPACK-41 adds the `core/api` exception so the shell shares the authoritative schema instead of mirroring it. The Audit log screen and reusable AuditTimeline belong to admin, keeping frontend dependencies out of core. A host's `core.audit` route replaces the built-in route and navigation entry.
