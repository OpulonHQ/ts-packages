# The host's public site reads the CMS only through the Read API

The host app renders its public pages by calling the cms Read API, not the cms services. On Workers the call is dispatched in-process to the composed handler, so there is no network subrequest. Elsewhere the same typed client uses a real `fetch` to a URL. Drafts, revisions and media-id resolution stay behind the Read API, so the cms can change its internals without breaking hosts, and the public site is just another client of the same contract that browsers and other sites use. Because an in-process call skips the edge cache, SSR copies the Read API's cache tags onto the page response, so the edge caches the page and publishing purges it by tag.

We rejected calling the cms services directly from host pages, which would couple every host to Effect and turn the internal service API into a public, semver-bound contract. We also rejected a real self-fetch (a service binding to itself), which still misses the edge cache and costs an extra invocation. When a page needs something the Read API cannot express, the Read API is extended, not bypassed. Decided in TSPACK-8.
