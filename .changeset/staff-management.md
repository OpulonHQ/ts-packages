Staff management gains four actions, each with an endpoint under `/api/users`, a place in the admin and an audit event. A user manager (`users.manage`) edits a user's name and email on the user screen: `PUT /users/:id` with `{ name, email }` answers 409 when another user has the address and 400 for one sign-in would not accept (the rule `importUsers` applies), before anything changes. A changed email ends that user's sessions and cancels the password reset links already sent to the old address (`users.updated`). A manager who changes their own email lands on the sign-in screen. The Users screen lists open invitations under the users table: `GET /invitations` returns every invitation not yet accepted, expired ones marked; `POST /invitations/:id/resend` emails a new link with the same roles and the old link stops working (`users.invited` again); `DELETE /invitations/:id` revokes one (`users.invitation_revoked`). Both refuse an invitation that grants a role the manager may not grant. A role manager (`users.roles.manage`) deletes a role from the role editor: `DELETE /roles/:id` answers 409 while any user holds the role, deactivated users included, and refuses Super admin (`users.role_deleted`). Every signed-in user changes their own password on My account: `PUT /password` with `{ currentPassword, newPassword }` ends the user's other sessions and keeps the one that sent it (`users.password_changed`). It needs no password confirmation; a wrong current password answers 403 `WrongPassword`, counts against the confirmation's 5 attempts a minute per client address and writes `users.password_confirmation_failed`. `UserManagement` gains `updateUser` and `deleteRole`; `Users` gains `invitations`, `resendInvitation`, `revokeInvitation` and `changePassword`. No migration and no new config key.
