# Read API answers are edge-cached and purged by tag; the database cache stays off

Every successful Read API answer carries `Cache-Control: public, max-age=0, s-maxage=86400` and a `Cache-Tag` header naming what it was built from: `cms`, the page or item itself, its collection, the site, or `cms:routes` for redirects, not-found answers and sitemaps. A page also carries the tags of the pages and items its links point at, so a renamed target refreshes every page linking to it. Publishing, unpublishing, deleting and redirect writes purge the affected tags after the transaction commits, through `CachePurge`; the host provides `cloudflareCachePurge()` in its infra with `CMS_CLOUDFLARE_ZONE_ID` and the `CMS_CLOUDFLARE_API_TOKEN` secret (Cache Purge permission). A failed purge is logged and the answer expires with its `s-maxage`. The public site's SSR copies the tags onto its HTML (ADR 0004).

The host's Hyperdrive configuration must have query caching disabled (`wrangler hyperdrive create <name> --caching-disabled`, or `update --caching-disabled`). Hyperdrive caches reads for up to 60 seconds and never invalidates on write, so a purged page would be rebuilt from stale rows. One binding serves the Worker, so admin reads after a write are fresh too.

We rejected purge-by-URL (the old sites' hardcoded path lists missed pages that link to a changed one) and an in-memory server cache (per isolate, never purged). Media edits do not purge yet: a replaced file gets a new URL and the old one keeps serving, so a cached page shows the previous version until its `s-maxage` runs out. Decided in TSPACK-11 and TSPACK-35.
