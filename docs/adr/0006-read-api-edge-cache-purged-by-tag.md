# Read API answers are edge-cached in Workers Cache and purged by tag; the database cache stays off

Every successful Read API answer carries `Cache-Control: public, max-age=0, s-maxage=3600` and a `Cache-Tag` header naming what it was built from: `cms`, the page or item itself, its collection, the site, or `cms:routes` for redirects, not-found answers and sitemaps. A page also carries the tags of the pages and items its links point at, so a renamed target refreshes every page linking to it. A header stays under 8 KiB (Cloudflare refuses Cache-Tag headers above 16 KiB): past that, the per-page and per-item tags collapse into `cms:routes`, which every page or item publish, unpublish and delete purges, so invalidation stays complete, only coarser; a header still above 8 KiB (an SSR page reading many collections) is not edge-cached at all: no Cache-Tag and `private, no-store`. The public site's SSR copies the tags onto its HTML (ADR 0004).

The cache is the Worker's own [Workers Cache](https://developers.cloudflare.com/workers/cache/): the host's Wrangler config sets `"cache": { "enabled": true }`, and Cloudflare answers a cached URL without running the Worker. Publishing, unpublishing, deleting and redirect writes purge the affected tags after the transaction commits, through `CachePurge`; the host provides `workersCachePurge(ctx)` in its `infra(env, ctx)`, which calls the invocation's [`ctx.cache.purge({ tags })`](https://developers.cloudflare.com/workers/cache/purge/). No zone or API token is involved. A purge is scoped to the Worker entrypoint that runs it, so a public site that renders in the same Worker and calls the composed handler in-process with its own `ctx` purges its HTML together with the Read API answers. Purges count against the account's purge limits, and Workers Cache always gets the Free tier's (5 requests per minute, bursts of 25, 100 tags per request) whatever the plan. A refused purge is retried twice, 12 seconds apart (one token's refill), inside the 30 seconds `waitUntil` keeps the Worker alive; a purge still refused, or failed, is logged, and the answer expires with its `s-maxage`. That is why `s-maxage` is one hour, not a day: it bounds how long a lost purge leaves an unpublished or deleted page public. A durable purge queue was rejected: it would need a cron or a queue, and one lost purge costs at most an hour.

Workers Cache keys a response by its URL only (cookies and `Authorization` are not part of the key) and caches a 200 without `Cache-Control` for two hours. So answers are private unless declared public. `createWorker` answers anything without its own `Cache-Control` with `private, no-store`. On a Nuxt site, `cmsNitroHooks` makes a page public only when the page calls `useCmsPublicPage()` during its render, declaring that nothing in it depends on the visitor: cms reads alone cannot prove that, since the same render may show the visitor's session. Even then the page stays `private, no-store`, untagged, if any read was `?preview`, carried credentials or was not public. Every other Nuxt answer without a `Cache-Control` gets `private, no-store` at the Worker's response boundary: `cmsNitroPlugin` wraps `nitroApp.localFetch`, through which the cloudflare-module preset answers every request, so the default holds however the answer was sent (`send`, `sendStream`, `sendRedirect`, `sendWebResponse`, `res.end`, route-rule redirects, error pages). Nitro's `beforeResponse` hook was not enough: direct sends skip it. A `Cache-Control` the host or an earlier hook set is never replaced, so no header value has to be told apart from a default. Nuxt's error pages are `private, no-store` too: Nitro renders them through the same `localFetch` and copies that answer's headers.

The host's Hyperdrive configuration must have query caching disabled (`wrangler hyperdrive create <name> --caching-disabled`, or `update --caching-disabled`). Hyperdrive caches reads for up to 60 seconds and never invalidates on write, so a purged page would be rebuilt from stale rows. One binding serves the Worker, so admin reads after a write are fresh too.

We rejected purge-by-URL (the old sites' hardcoded path lists missed pages that link to a changed one) and an in-memory server cache (per isolate, never purged). We first purged through the zone API (`POST /zones/<zone>/purge_cache` with a token), but a Worker's own responses are not stored in the zone cache, and no zone-level purge reaches Workers Cache (TSPACK-38). Media edits do not purge yet: a replaced file gets a new URL and the old one keeps serving, so a cached page shows the previous version until its `s-maxage` runs out. Decided in TSPACK-11 and TSPACK-35, revised in TSPACK-38.
