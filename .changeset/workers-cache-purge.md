Breaking: the cms purges cached answers from the Worker's own Workers Cache instead of the zone cache, which never held a Worker's responses. `cloudflareCachePurge()` and its `CMS_CLOUDFLARE_ZONE_ID` / `CMS_CLOUDFLARE_API_TOKEN` settings are gone; put `workersCachePurge(ctx)` in `infra` and set `"cache": { "enabled": true }` in the Wrangler config. A purge also clears a Nuxt site's HTML when it runs in the same Worker and calls the API in-process. A purge refused by the rate limit is retried twice, 12 seconds apart, and Read API answers now carry `s-maxage=3600` (was a day), so a lost purge leaves them stale for an hour at most. On Workers, a Nuxt page is cached publicly only when it calls the new `useCmsPublicPage()` during its render and every cms read was public; every other answer without a Cache-Control, however it was sent, gets `private, no-store` from the new `cmsNitroPlugin(worker)` (`export default defineNitroPlugin(cmsNitroPlugin(worker))`, which replaces wiring `cmsNitroHooks` by hand), and a host's Cache-Control is never replaced. core: `createWorker` passes the invocation's `ctx` to `infra(env, ctx)` (and `scheduled` accepts it), `WorkerContext` gains the optional `cache`, and an answer without its own `Cache-Control` is sent `private, no-store`, so Workers Cache never stores a session's reads.
